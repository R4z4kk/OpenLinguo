# M8 sync Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Two devices of one account converge, deletions included, through opt-in sync.

**Architecture:** Dexie hooks record each change in `syncEntities`. The device gzips waiting changes into chunks and posts them; `/api/sync` stores them as opaque bytes in D1 and hands them back one per request. Each device validates and merges what it receives.

**Tech Stack:** Dexie 4, zod, `CompressionStream`, Hono, Drizzle on D1, Vitest with fake-indexeddb and the API's `migratedPlatform`, Playwright with axe.

**Spec:** [ADR 0016](../../adr/0016-sync.md)

## Global Constraints

- All code, names, comments and commits in English; minimal comments; no `any`, no `undefined` (`no-undefined` lint rule); failures as `Result`, never a silent default.
- One issue per task on milestone M8, listed in epic #36; one PR per task to `develop`; "Closes #N". No `Co-Authored-By` in commits.
- Limits, from the spec: 256 KiB per chunk, 10 MiB per account, 120 chunks an hour per account, no new chunk once `meta.size_after` exceeds 400 MB; automatic sync at most every 5 minutes.
- Synced: reviews, cards, decks, deckWords, notes, knownMarks. Never: journal, challenges, texts, settings, audio, voice, AI key.
- The repository is public: no real addresses, IPs or findings in tests, issues or docs.
- Strings in French and English; no prompt after a session; no notification.
- Local E2E on WebKit does not run on Windows: use `--project=chromium` locally and dispatch `ci` on the branch for WebKit.
- A task changing a Dexie version takes the next free one at merge time; this plan assumes 25.

## Review Focus

1. A database upgraded from an old version (v8 to v24) with data must open: the hook's scope guard must not fire during `versionchange`. Test in Task 2.
2. Two devices that each created a deck named « Voyage » must both end with both decks, each with its words, whichever chunk arrives first, and a rename or deletion of one must lose nothing of the other. Test in Task 3.
3. A note too large for one chunk must stop sending with a visible failure, and leave everything else waiting, rather than loop or be dropped. Test in Task 4.
4. Two tabs open at once must not send the same waiting rows twice, and a crash between the server's answer and the local update may resend a chunk with no harm. Test in Task 4.
5. A failure in the account export's sync part must fail the export visibly, not produce a file that silently lacks the synced data. Test in Task 6.

**Interfaces:**

- Consumes: `SyncEntity`, `silently`, `SyncState` from Task 2.
- Produces in `sync-chunk.ts`:

  - `SyncChunk`, zod `{ format, version, reviews: Review[], entities: SyncedEntity[] }`, where `SyncedEntity` is a discriminated union on `table` holding `key`, `changedAt`, `deleted` and `value`, `null` when deleted, each `value` validated with the schema `Backup` uses for that table
  - `encodeChunk(chunk: SyncChunk): Promise<Uint8Array>`
  - `decodeChunk(bytes: Uint8Array): Promise<Result<SyncChunk, ChunkFailure>>`, `type ChunkFailure = { kind: "unreadable" } | { kind: "newer-format"; version: number }`
- Produces in `sync-merge.ts`: `applyChunk(db: Database, chunk: SyncChunk, chunkId: number): Promise<Result<null, ReviewLogFailure>>`, one transaction, moving `syncState.cursor` to `chunkId`.

- [ ] **Step 1: Write the failing tests**, two databases standing for two devices, exchanging chunks:
  - `decodes what it encodes`; `a corrupted chunk is unreadable`; `a higher version is newer-format`; `an invalid row is unreadable`.
  - `two devices converge whatever the order`: apply `[a, b]` to one and `[b, a]` to the other, then compare every synced table.
  - `the same chunk twice changes nothing`.
  - `a later deletion wins, an earlier one loses`; `on a tie the deletion wins, then the larger serialized value`.
  - `a word whose deck was deleted goes with it`, and a card filed since stays on both devices.
  - `a device whose clock is behind edits a row it received, and both keep the edit`, and the same with a deletion.
  - `devices on different referentials converge`.
  - `a note deleted while filed elsewhere comes back`, whichever device hears first, with no ghost queued meanwhile; `a note with no live filing is deleted everywhere`; `a later real deletion by the device holding the filing deletes it everywhere`.
  - `a review of an unknown card is kept, and the card's state appears when the card arrives`.
  - `card states match a replay of the merged log`, on cards touched by the chunk.
  - `same-name decks stay separate and both devices hold both, with their words`, in both orders, and when one device renames or deletes its deck before hearing of the other (Review Focus 2).
  - `applying records nothing to send`; `a failure leaves the tables and the cursor untouched`.

- [ ] **Step 2: Run them**: `pnpm exec vitest run apps/web/src/data/sync-chunk.test.ts apps/web/src/data/sync-merge.test.ts`. Expected: FAIL.

- [ ] **Step 3: Implement `encodeChunk` and `decodeChunk`** with `CompressionStream("gzip")` and `DecompressionStream("gzip")`. Check the version with a loose header schema first, as `backup.ts:61` does, so a newer format is told apart from a broken one.

- [ ] **Step 4: Implement `applyChunk`.** The rule that decides a change, which the tests alone do not determine:

```ts
const wins = (incoming: SyncedEntity, local: SyncEntity | null, localValue: unknown): boolean => {
  if (local === null) return true;
  if (incoming.changedAt !== local.changedAt) return incoming.changedAt > local.changedAt;
  if (incoming.deleted !== local.deleted) return incoming.deleted;
  return JSON.stringify(incoming.value) > JSON.stringify(localValue);
};
```

  - After a win, write the value or delete it, and store the row with `pending: 0` and the incoming time.
  - Decks of the same name stay separate. A merge would depend on what each device held when it looked, so it would not converge, and could delete a deck on one device only. `importBackup` keeps its own merge by name, on the device's own choice.
  - An incoming note deletion that would win, on a device with a live `deckWords` row for that note and its value: keep the row and store its `syncEntities` row with `deleted: false`, `pending: 1` and `changedAt` of `incoming.changedAt + 1`, so every device adopts it. With no live filing or no value, the deletion stands. `nextNewReadings` skips a note with no content, so a filing waiting for its note queues nothing.
  - Each row follows from what is known of it, and `applyChunk` does not call `dropUnfiled`. Accepted exception: a restored backup that brings back a deck deleted elsewhere leaves its contents different until a word next changes. A word's row exists while its entity is live and its deck is not known to be deleted; its entity stays when the deck goes, so a deck coming back files its words again.
  - Replay only the cards the chunk's reviews touch, with `replay`, as `recordReview` does; skip cards not present.
